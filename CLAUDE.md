# CLAUDE.md

Guidance for Claude Code in this repo.

## What this is

A **public** GitHub repo: a pytest suite for the SpireScape game server (tested from outside, over the same WebSocket protocol the browser client uses), evals for an AI email classifier, and a generator for the report page that shows both. The SpireScape source and the classifier live in private repos; nothing here may copy from them beyond what any player's browser already receives.

The suite and its tooling stay Python on pytest (the owner's decision, 2026-10-29): the repo is there to show pytest work. The megaproject's move to TypeScript stops at the report page's script, so new or changed tests and tooling are Python, and don't offer to port them.

The test code is drafted with Claude. Since October 2026 the suite runs with no human review, as an experiment: Claude reviews every run, the deterministic checks decide what the review may claim, and the owner hasn't reviewed tests yet. Never write that the owner reviews every test, or that decisions sit on suggestions that are still open. `review.json` (written by `ql review`) records any test the owner does review or rewrite, and the page shows that count honestly.

## Never commit personal data

- No real names beyond the public handle, no emails, phone numbers, machine names, employers, or absolute paths from a real machine (write `~`).
- Run records (`history/`) are generated by `qualitylab/results.py`, which strips home paths from failure text. Check any hand-written fixture data the same way.
- The leak check (`scripts/leak-check.sh`) runs from `.githooks/` on commit, commit message and push: gitleaks plus a private blocklist at `~/.config/quality-lab/blocklist.txt` (never copy its entries anywhere). The blocklist and `allowed-identities.txt` never leave this PC, not even as GitHub secrets (the owner's rule, 2026-10-21; the repo's old `QL_BLOCKLIST` and `QL_ALLOWED_IDENTITIES` secrets were deleted that day), so GitHub's leak check runs gitleaks alone. Each clone needs `git config core.hooksPath .githooks`. Never skip it with `--no-verify`.
- That hooksPath replaces the machine's own hooks folder (the global `core.hooksPath`), so on a clone with `namemask.mode` set in its git config (this PC's, since 2026-10-22) each hook first hands over to the machine's hook of the same name through `scripts/machine-hook.sh`, and a missing one blocks (`tests/unit/test_hooks.py`). Those hooks are another project's, found through git config: never write their path, or what they check, into this repo. A clone without `namemask.mode` (CI, anyone else's) runs the leak check alone.
- Commit with the public noreply identity set in this repo's local git config.

## Targets

- `--target local` (default): builds the server from a SpireScape checkout named by `SPIRESCAPE_REPO`, one server per xdist worker, 20 ms tick, seed 7. Runs everything.
- `--target live`: the public demo at its real 600 ms tick. Skips `local_only` tests (hostile input, seeded or time-skipping checks). Use `--dist loadgroup`: combat tests share an `xdist_group` because the map has two rats.

Known bugs are `xfail(strict=True)` with a `BUG-nnn` id in the reason, so a fix shows up as an XPASS failure and the marker has to be removed on purpose. BUG-008 is the exception: intermittent (some upgrades to the live demo are never answered), so `test_every_upgrade_is_answered` measures it and xfails imperatively on live when it's seen, `connect` tries a stalled connect once more on live and records it (a metric and a warning), and the page shows the finding as seen or unseen from its `metrics` list. A bug only the live demo has (BUG-009) is marked `xfail_live(reason)`, which `conftest.py` turns into a strict xfail on live and leaves a plain test locally.

## Commands

```powershell
uv sync
npm ci                                                              # esbuild and TypeScript 7, for the report page's script
$env:SPIRESCAPE_REPO = "<path to a SpireScape checkout>"
uv run pytest tests -n 4                                            # local, everything
uv run pytest tests/spirescape --target live -n 4 --dist loadgroup  # the public demo
uv run pytest tests/unit                                            # no server

uv run ql run --target local|live     # a recorded run into history/runs/
uv run ql analyse                     # AI review + suggestions
uv run ql eval email                  # needs EMAIL_DASHBOARD_DIR
uv run ql pull                        # CI's live run records (its live-run artifacts) into history/runs; gh, logged in
uv run ql build                       # build/index.html
uv run ql review <id-substring> --status reviewed|rewritten
uv run ql suggestion S-001 --status accepted|rejected|done --note "..."
```

CI (`.github/workflows/`): the leak check, unit tests on every push, and the live suite on every push and nightly. CI can't run the local target (the server source is private), and it can't commit, so its run records come back with `ql pull` (each run's `live-run` artifact) and get committed like any record.

**Check: `uv run pytest tests -n 4`** (local target). Nothing merges into `main` until it passes.

**Actions:** no dashboard yet; every action is a command above: pytest, and `ql run`, `pull`, `analyse`, `eval`, `build`, `review` and `suggestion`. `ql review` and `ql suggestion` record the owner's own decisions, so they run only on the owner's word, and `ql analyse` and `ql eval` call Claude. Putting the built page online belongs to the private site's publishing, not to this repo.

## Git

A feature branch (`feat/...`, `fix/...`, `docs/...`) in a worktree under `.claude/worktrees/` (git-ignored), however small the change: the main checkout never leaves `main`. Drive the worktree with `git -C <worktree>` rather than changing into it. Commit each working step, then land the branch once the check passes, with the owner's `land` command: `land <branch> -m "<what it does>. Check passed"`. It makes the `--no-ff` merge into `main` itself, brings the main checkout forward, and removes the worktree and the branch; never merge into `main` by hand. It doesn't push this repo. Pushing to GitHub is a publish: only when the owner asks.
